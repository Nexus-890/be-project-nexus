# Code và cách trình bày #106, #109, #122, #123

Đọc theo thứ tự bên dưới. Bốn issue chia thành ba luồng: category phát sự kiện,
notification đánh dấu đã đọc, và quản lý ảnh sản phẩm.

## 1. #104 tạo nền outbox; #106 đưa category vào nền đó

Ví dụ: tạo category thành công trong PostgreSQL nhưng Kafka đang tắt. Nếu API
gọi Kafka trực tiếp, dữ liệu có thể đã lưu mà sự kiện lại mất. Outbox giải quyết
bằng cách lưu **category và một dòng sự kiện trong cùng transaction PostgreSQL**.
Transaction là nhóm thao tác cùng commit hoặc cùng rollback.

#104 đã cung cấp thư viện `lib/common-outbox`:

- `OutboxWriter`: INSERT sự kiện vào bảng outbox, bắt buộc có transaction sẵn
  (`PROPAGATION_MANDATORY`). Nó dùng chung datasource/transaction manager với service.
- `OutboxRelay`: tác vụ nền lấy dòng `published_at IS NULL`, gửi Kafka, đợi ACK
  rồi mới cập nhật `published_at`. Kafka lỗi thì giữ dòng chờ lần chạy sau.
- `OutboxAutoConfiguration`: nối các thành phần trên vào Spring.

Đây là code #106 thêm vào `catalog-service/.../category/CategoryService.java`:

```java
@Transactional
public CategoryResponse create(CategoryRequest request) {
    // ...kiểm tra đầu vào, tạo entity...
    Category saved = categoryRepository.saveAndFlush(category);
    writeCategoryEvent("CategoryCreated", saved.getId(), new CategoryCreatedPayload(
            saved.getId(), saved.getName(), saved.getSlug(), saved.getParentId()));
    // ...trả response...
}
```

Đoạn trích có lược bỏ phần không liên quan. `saveAndFlush` đẩy SQL xuống DB,
**chưa commit**; exception sau đó vẫn rollback cả category và outbox. Update
ghi `CategoryUpdated`; cả hard delete và soft delete ghi `CategoryDeleted` sau
khi các điều kiện xóa đã qua. Created/Updated có categoryId, name, slug, parentId;
Deleted chỉ có categoryId, đúng schema trong `docs/api/events.md`.

Helper bọc payload thành `EventEnvelope` có eventId, eventType, aggregateId,
occurredAt, traceId, rồi gọi:

```java
outboxWriter.write("Category", Topics.CATALOG, envelope);
```

Trong relay của #104, phần quyết định thứ tự xử lý là:

```java
kafka.send(entry.topic(), entry.aggregateId(), envelope)
        .get(sendTimeoutMillis, TimeUnit.MILLISECONDS);
jdbc.update(MARK_PUBLISHED_SQL, entry.id());
```

Topic là `nexus.catalog.events`, key là categoryId. Khi Kafka tắt, API vẫn có
thể trả 201 vì nó chỉ cần commit DB. Relay sẽ gửi lại sau. Nếu Kafka nhận rồi
process chết trước khi commit dấu published, sự kiện có thể gửi lại với cùng
eventId: đây là **at-least-once**, consumer cần chống xử lý trùng (#105).
Kiểm thử đã chứng minh thứ tự với một relay; chưa bảo đảm thứ tự theo category
khi nhiều relay cùng chạy. Không trình bày là exactly-once.

**Tự kiểm:** `CategoryOutboxIntegrationTest` dừng broker riêng, tạo category,
kiểm tra dòng pending; gây rollback và kiểm tra cả hai bảng không có dòng;
bật lại broker, consume Created → Updated → Deleted, kiểm tra key/offset và schema.
Lần chạy lại 30/10: **55 test catalog đạt**, gồm 10 test này.

## 2. #108 đã có list/count; #109 thêm đánh dấu đã đọc

`notification-service/.../notification/NotificationService.java` lấy userId từ
JWT (`CurrentUser`), không nhận userId tùy ý từ request. Code mark một dòng:

```java
Notification notification = repository.findById(id)
        .orElseThrow(() -> new DomainException(NotificationErrorCode.NOT_FOUND));
if (!userId.equals(notification.getUserId())) {
    throw new DomainException(NotificationErrorCode.NOT_OWNER);
}
if (notification.getReadAt() == null) {
    repository.markAsRead(id, userId, OffsetDateTime.now(ZoneOffset.UTC));
}
```

Không có dòng → 404; dòng của người khác → 403; đã đọc → 204 và không ghi lại.
`PATCH /api/v1/notifications/read-all` dùng đúng **một UPDATE** trong repository:

```sql
UPDATE Notification n SET n.readAt = :readAt, n.updatedBy = :userId
WHERE n.userId = :userId AND n.readAt IS NULL
```

Đây là JPQL, dùng tên entity/field Java. Điều kiện userId cô lập dữ liệu của A/B;
điều kiện readAt tránh thay đổi dòng đã đọc. Cả hai PATCH trả 204, không có body,
và yêu cầu privilege `NOTIFICATION.VIEW` ở gateway/service.

**Tự kiểm:** `NotificationMarkReadIntegrationTest`: A gọi ID của B phải 403 và
toàn bộ row không đổi; A có 3 unread thì read-all → 204, unread-count → 0, B vẫn
unread; gọi lại không đổi dữ liệu. Hibernate statistics kiểm tra một UPDATE.
**41 test notification và 41 test gateway đạt trên nhánh #109.**

## 3. #122 upload; #123 xóa, đổi thứ tự và seed ảnh

Ảnh có hai phần: bytes trong Supabase và metadata trong bảng `product_images`
(id, productId, imageUrl, sortOrder). #122 kiểm tra MIME từ bytes, giới hạn
5 MB/5 ảnh mặc định, kiểm tra seller sở hữu product, upload rồi lưu URL.
Khóa dòng product ngăn hai request cùng vượt giới hạn số ảnh.

Đợt audit #122 đã sửa response về `ApiResponse<ImageResponse>`, lỗi thành
`CATALOG_*`, thêm ảnh có thứ tự vào product list bằng một query theo batch,
và cập nhật OpenAPI/inventory. **67 test catalog đạt**; upload JPEG 200 KB qua
Supabase thật đã trả 201, lưu row, URL trả 200 và giải mã ảnh được.

#123 dùng lại khóa product cho cả upload/delete/reorder. Trong
`catalog-service/.../product/ProductImageService.java`, delete thực hiện:

```java
requireOwnedProduct(productId, user);
ProductImage image = images.findById(imageId)
        .filter(candidate -> candidate.getProduct().getId().equals(productId))
        .orElseThrow(() -> new DomainException(CatalogErrorCode.IMAGE_NOT_FOUND));
images.delete(image);
images.flush();
storage.delete(productId, image.getImageUrl());
```

Method có `@Transactional`. Sai chủ → 403; ảnh không thuộc product → 404;
storage lỗi → 503 và rollback DB. `ImageStorageClient.delete` chỉ xóa đường dẫn
thuộc host/bucket/product đã cấu hình. Thành công → bodyless 204.

Reorder nhận `{"imageIds":["ID_B","ID_A"]}`. Service kiểm tra số lượng, không
trùng/null, tập ID bằng chính xác toàn bộ ảnh hiện tại, rồi mới ghi:

```java
for (int i = 0; i < imageIds.size(); i++) {
    byId.get(imageIds.get(i)).setSortOrder((short) i);
}
images.flush();
```

B đứng đầu có sortOrder 0, A có sortOrder 1; product detail trả đúng thứ tự đó.
Thiếu/trùng/ID lạ → 400 trước khi sửa dữ liệu. PUT trả ApiResponse có data và
page. Hai endpoint yêu cầu SELLER + PRODUCT.UPDATE + ownership trong service.

`V7__seed_images.sql` thêm một URL cho mỗi sản phẩm demo của V3. Dùng V7 vì V5/V6
đã tồn tại, không sửa migration đã chạy. Ảnh minh họa và script provision nằm ở
`infra/local-dev/seed-images` và `provision-product-images.ps1`; cả 5 URL thật đã
tải được và khớp bytes ảnh nguồn. Ba điện thoại dùng chung ảnh minh họa.

**Giới hạn cần nói rõ:** PostgreSQL và Supabase không chung transaction. Storage
từ chối xóa thì DB rollback; nhưng process/DB commit lỗi sau khi file đã xóa vẫn
có thể để lại row trỏ tới file mất. Upload cleanup cũng là best effort.

**Tự kiểm #123:** upload hai ảnh vào product thử, PUT đảo ID rồi GET detail;
PUT thiếu một ID phải 400 và DB không đổi; seller B DELETE ảnh của A phải 403;
seller A DELETE phải 204, DB mất row, kiểm tra URL cũ. Không xóa ảnh seed dùng chung.
**76 test catalog + 40 test gateway đạt** trên nhánh #123, gồm 13 test ảnh với
PostgreSQL và filter thật; storage mặc định là HTTP fixture, JWT decoder giả lập.

**Mục chưa đạt, giữ nguyên theo yêu cầu:** Supabase thật trả HTTP **400** kèm
`statusCode: "404"` khi GET ảnh đã xóa. Bài test strict HTTP 404 đã fail; kiểm
tra chẩn đoán riêng xác nhận hành vi 400 + 404 trong body. Không tính chẩn đoán đó
là đạt tiêu chí HTTP 404. Nguồn về legacy errors:
https://supabase.com/docs/guides/storage/debugging/error-codes#legacy-error-codes
